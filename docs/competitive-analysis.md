## Position

The existing README tried to distinguish Pulsecheck by saying other debuggers
were viewers and therefore poor evidence. That is no longer accurate. Several
competitors export data, and Tag Master explicitly advertises a Markdown audit.

The useful distinction is the shape of the artifact:

- network, data-layer and consent records share one ordered timeline;
- every exported row has a stable sequence number;
- consent is replayed after sorting by send time;
- PII is redacted before the file is created;
- unknown first-party collectors are retained;
- Markdown and JSONL are generated from the same event list; and
- the repository includes a defined analysis workflow for the exported file.

A concise store description would be:

> Record one tracking scenario as an ordered Markdown or JSONL file. Pulsecheck
> captures network hits, dataLayer pushes and consent changes in Chrome
> DevTools, redacts detected PII before export, and keeps sequence numbers for
> audit evidence.

Avoid claims about being the only consent auditor, the only exporter or the
broadest debugger. The code does not support those claims.

## Store assets

Use three screenshots, in this order:

1. the real DevTools panel during a session;
2. an expanded event showing the full captured payload; and
3. a real Markdown file generated by `export.js`.

The first two should use actual captures rather than reconstructed interfaces.
The third should show the file itself because the file is the main product.

The repository includes an anonymized sample dump so a potential user can
inspect the output without installing the extension.

## Product work after v0.1

Session diff and tracking-plan diff are more useful differentiators than adding
dozens of parsers. Add named vendors when they appear in real audits. Adobe and
Tealium are the largest visible coverage gaps, but they should not delay fixes
to redaction or Chrome integration testing.
