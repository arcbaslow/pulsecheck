# Pulsecheck privacy policy

Effective 7 September 2026. Applies to Pulsecheck 0.1.1 (alpha).

This policy forms part of the Goodlabs privacy policy published at
<https://goodlabs.kz/privacy#pulsecheck>, which is the canonical version and
which also states the rights available in respect of personal information and
how to exercise them. Where this file and the published policy differ, the
published policy governs.

Pulsecheck is published by Goodlabs, operated by Dilshat Rakhimov, Almaty,
Kazakhstan.

Pulsecheck is a panel extension for Chrome DevTools. It records the measurement
activity of the tab on which DevTools is open and produces a file describing
that session at the user's request.

## 1. Information processed

While the panel is open and recording, Pulsecheck processes the following from
the tab being inspected:

- the address of the inspected page and each subsequent navigation;
- outgoing tracking requests, comprising the URL, method, request body,
  response status code and MIME type;
- messages pushed to `dataLayer`, `digitalData` and other arrays whose name
  contains `datalayer`;
- Google Consent Mode values and changes to them;
- the browser user-agent string;
- the scenario note entered by the user.

Tracking payloads are generated by the site under inspection and not by
Pulsecheck. They may contain personal information relating to the person
browsing that site, placed there by that site. Identifying such information is
the purpose for which a tracking audit is performed.

An optional setting, **API context**, is disabled by default and requires
confirmation to enable. When enabled it additionally records the method, host,
path, status and MIME type of the inspected site's non-tracking requests.
Request bodies and query strings are excluded from it.

## 2. No transmission to Goodlabs

Pulsecheck has no backend service, no API endpoint, no analytics and no account
system. The extension contains a single `fetch()` call, which reads the file
`tap.js` from within the extension package.

No data from a session is transmitted to Goodlabs or to any third party. No
third-party script, software development kit or error-reporting service is
included in the extension.

## 3. Storage and retention

A session is held in the memory of the DevTools panel. It is discarded when
DevTools is closed, when the extension is reloaded, or when the user clears the
timeline.

The inspected page also holds a temporary buffer of data layer messages. The
panel drains it every 500 ms while recording. Pausing or closing the panel
explicitly stops the tap and clears this buffer. If that stop cannot run, a
60-second fallback recording lease expires and clears it at the next timer tick or
push. No further pushes are recorded until the panel renews the lease.

Pulsecheck does not use `chrome.storage`, `localStorage`, `sessionStorage` or
IndexedDB. Page-owned data layer arrays are not cleared by Pulsecheck.

## 4. Exports

A file is produced only when the user selects Save Markdown, Save JSONL or
Copy. The file is generated locally and passed to the browser's download or
clipboard functions.

An export is thereafter under the user's control and is deleted by the user.
Goodlabs does not receive a copy of any export.

## 5. Redaction applied to exports

Before an export is generated, Pulsecheck masks values it is able to identify.
The panel display is not masked, as it shows the user their own session. The
following are masked:

- detected email addresses, telephone numbers and IPv4/IPv6 addresses in string
  values in parameters, including JSON and form-encoded request bodies;
  request URLs, page URLs and absolute HTTP(S) URL-valued parameters also have
  their authority, query parameters, path segments and fragments inspected;
- values under keys denoting a person or a personal identifier, among them
  `user_id`, `email`, `phone`, `first_name`, `surname`, `iin` and `passport`,
  which are masked while retaining their shape;
- values under keys denoting a secret, among them `password`, `api_secret`,
  `apiSecret`, `secret`, `token`,
  `authorization`, `cookie`, `card_number`, `cvv` and `iban`, which are
  replaced in full with `[redacted]`.

URL-valued parameters receive URL-aware handling after parsing, including
values in JSON and form-encoded bodies. Hosts detected as IP addresses or phone
numbers are replaced with `redacted.invalid`.
JSON and form values decoded from parser-error `raw` bodies receive the same
URL-aware handling. Parser-error `raw` bodies receive JSON/form decoding and
inline detection; standalone URL strings and
multipart parts do not receive URL-aware handling.

IP detection applies only to whole trimmed address values or values under
IP-like keys (`ip`, `ip_address`, `client_ip`, `remote_addr`, `x-forwarded-for`,
`uip`, `_uip`). It excludes `uafvl`, `uapv` and keys containing `version` to avoid
mistaking software versions for IP addresses.

Path segments use the previous segment as their key. This can mask ordinary
identifiers: `/pin/123456789` is masked as a secret and `/order/87771234567` as a
phone number. This trade-off favours hiding sensitive values over preserving
every path identifier.

Redaction uses key names and value patterns and is incomplete. Unrecognised
formats, unnamed tokens and personal information in free text can escape
detection. Certain identifiers, among them client ids (`cid`), `event_id`,
`insert_id` and `api_key`, are retained deliberately because the audit needs
them. In request URLs, inline detection can still mask phone-shaped KEEP values
(for example, `_p=81234567890`), while the same value in `params` is retained;
this favours hiding possible phone numbers over preserving unusual identifiers.
Every event name undergoes inline pattern detection, and paths in
`METHOD /path` names use the same segment rules as URL paths. Event names and
audit-subject fields such as `event_name`, `page_name`, `item_name` and
`product_name` are not treated as person-name keys; their string values still
undergo pattern-based detection. Scenario notes and the user-agent string are
not redacted.

Users must review an export before disclosing it to any third party. Pulsecheck
is alpha software and its redaction is a mitigation, not a guarantee.

## 6. Modification of the inspected page

To observe data layer messages, Pulsecheck injects a script into the inspected
page using `chrome.devtools.inspectedWindow.eval`. The script replaces the
`push` method of arrays named `dataLayer` or `digitalData` with a wrapper that
records the message and then calls the original method, leaving the behaviour of
the page unchanged. The replacement is defined as non-enumerable and does not
appear in `Object.keys(dataLayer)` or in the page's own enumeration.

The script applies only to the inspected tab. Recording and scanning stop on
pause or panel close, with the 60-second lease as a fallback if the explicit
stop cannot run. Wrappers can remain installed until the page reloads, but pass
pushes through without recording while stopped. Resuming an existing tap skips
entries accumulated while stopped. If the page loaded while paused, resuming
injects a fresh tap whose first scan records that page's existing data layer
entries with the resume timestamp. No other part of the page is modified.

## 7. Permissions

The extension manifest declares no permissions. It contains no `permissions`
block and requests no host, `tabs`, `storage`, `webRequest` or `history` access.
Pulsecheck uses only the interfaces available to a DevTools extension in respect
of the tab on which the user has opened DevTools:

- `chrome.devtools.panels.create`, to register the Pulsecheck panel;
- `chrome.devtools.network.onRequestFinished`, to receive the requests made by
  that tab. Request bodies are taken from the data Chrome supplies, and response
  bodies are not retrieved;
- `chrome.devtools.inspectedWindow.eval`, to inject the data layer script
  described above and to read the page address and user-agent string.

The toolbar icon opens an informational popup stating where the panel is found.
It has no access to page content.

## 8. Chrome Web Store Limited Use

Pulsecheck's use of information received from Google APIs adheres to the Chrome
Web Store User Data Policy, including the Limited Use requirements.
Specifically:

- recorded data is used solely to display the session timeline and to generate
  the export the user has requested;
- recorded data is not sold, rented or transferred to any third party;
- recorded data is not used for advertising, retargeting, profiling or the
  assessment of creditworthiness;
- no person at Goodlabs has access to a user's session data, and no mechanism
  exists by which it could be obtained, unless the user elects to send an export
  for support purposes.

Pulsecheck serves a single purpose: recording and auditing measurement events
within Chrome DevTools.
